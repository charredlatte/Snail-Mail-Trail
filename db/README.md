# Database

PostgreSQL schema and sample data.

| File | Purpose |
|------|---------|
| `schema.sql` | Every table, index and constraint. Safe to re-run. |
| `seed.sql` | Fictional sample clubs for development. Delete before launch. |

Apply both with `npm run init-db -- --seed`.

## The tables

**`users`** — email, password hash, display name, role (`member` or `admin`).
Emails are lowercased by the app before they are stored, so a plain unique index
is enough and we avoid needing the `citext` extension.

**`sessions`** — one row per signed-in browser. Stores the SHA-256 *hash* of the
session token, never the token itself, so a leaked database dump cannot be
replayed as a login.

**`clubs`** — the directory. Covered in detail below.

**`tags`** / **`club_tags`** — categories (postcard, zine, pen pal…) and the
many-to-many join. A club can carry several.

## Decisions worth explaining

**Money is stored as integer cents**, never floats. `price_cents = 1250` is
$12.50. Floating point money is a bug waiting for a rounding edge case.

**`monthly_cents` is a generated column.** A club might charge $5/month and
another $90/year. Filtering "under $10 a month" has to compare those honestly,
so the database derives a monthly equivalent from `price_cents` and
`price_period`:

| `price_period` | `monthly_cents` |
|---|---|
| `free` | 0 |
| `monthly` | as-is |
| `quarterly` | ÷ 3 |
| `yearly` | ÷ 12 |
| `one_time`, `per_swap` | as-is |

Because Postgres generates it, it can never drift out of sync with the price it
was derived from — which is exactly what happens when the application computes
this and someone later updates a price through a different code path.

**Prices are normalised twice: for period, then for currency.** Filtering
"under $10 a month" has to work across a $5/month club, a $90/year club and a
GBP 14/month club. Three columns carry that:

| Column | Meaning | Used for |
|---|---|---|
| `price_cents` | the amount as charged, x100, in the club's own currency | display |
| `monthly_cents` | monthly equivalent, still in the club's currency | display |
| `usd_monthly_cents` | monthly equivalent converted to US cents | **all filtering and sorting** |

`fx_to_usd` is how many US dollars **one unit** of the club's currency buys, so
a GBP club stores about `1.27` and a JPY club about `0.0067`. Getting that
direction backwards is the easy mistake — it is USD-per-unit, not units-per-USD.

Rates are stored per club rather than looked up live, deliberately: a search
result should not change price because a currency moved overnight, and a
directory does not need real-time FX. `scripts/import-clubs.js` fills them in.

`fx_to_usd` is nullable, and NULL is treated as `1.0`. That is correct for USD
listings and wrong for every other currency, so the admin queue returns
`needs_fx_rate: true` for any non-USD listing still missing one.

**`price_cents` is always the amount x100, even for zero-decimal currencies.**
JPY 2500 is stored as `250000`, not `2500`. The exchange rate is scaled to
match, so conversion stays correct. The only consequence is cosmetic: a front
end should not print "JPY 2500.00" with decimals the currency does not use.

**The period maths lives in one function.** Postgres forbids a generated column
from referencing another generated column, and both `monthly_cents` and
`usd_monthly_cents` need the same period conversion. Duplicating the `CASE` into
each is how they would eventually drift apart, so it sits in
`monthly_equivalent_cents(cents, period)` instead, which must stay `IMMUTABLE`
for the generated columns to be allowed to call it.

Changing that function does **not** recompute already-stored rows. If you ever
change it, force a rewrite:

```sql
ALTER TABLE clubs ALTER COLUMN monthly_cents     DROP EXPRESSION;
ALTER TABLE clubs ALTER COLUMN usd_monthly_cents DROP EXPRESSION;
-- then re-run db/schema.sql's column definitions as ALTER ... ADD GENERATED
```

**`search_doc` is a generated `tsvector`** with weighted fields: a name match
(weight A) outranks a description match (B), which outranks a city match (C).
Also generated by the database, for the same reason.

**Coordinates are plain `DOUBLE PRECISION`**, not PostGIS. Distance is computed
with the haversine formula in SQL, after a bounding-box prefilter narrows the
candidates using the `(lat, lng)` index. This needs no extensions and is instant
at this scale. See "Known limitations" in the root README for when to change it.

**`status` drives all public visibility.** Public queries filter
`status = 'approved'` without exception, so a submission is invisible until a
human approves it. The indexes are *partial* — built `WHERE status = 'approved'`
— which keeps them small and matches exactly how they are queried.

## Changing the schema

There is no migration tool. `schema.sql` uses `IF NOT EXISTS` throughout, so
re-running it adds new objects without touching existing ones. To change an
existing column, write the `ALTER TABLE` by hand and update `schema.sql` to
match, so a fresh database and an upgraded one end up identical.

If this repo ever gets a second developer or a staging environment, that is the
moment to adopt a real migration tool.

### Upgrading a database created before currency conversion

An existing database needs the new objects added by hand once. Re-running
`schema.sql` creates the function but will not alter the existing `clubs` table:

```sql
-- 1. The helper function and the rate column
\i db/schema.sql                       -- creates monthly_equivalent_cents()
ALTER TABLE clubs ADD COLUMN IF NOT EXISTS fx_to_usd NUMERIC(14,6)
  CHECK (fx_to_usd IS NULL OR fx_to_usd > 0);

-- 2. Swap monthly_cents onto the shared function, and add the USD column
ALTER TABLE clubs DROP COLUMN monthly_cents;
ALTER TABLE clubs ADD COLUMN monthly_cents INTEGER
  GENERATED ALWAYS AS (monthly_equivalent_cents(price_cents, price_period)) STORED;
ALTER TABLE clubs ADD COLUMN usd_monthly_cents INTEGER
  GENERATED ALWAYS AS (round(monthly_equivalent_cents(price_cents, price_period)
                             * COALESCE(fx_to_usd, 1))::INTEGER) STORED;

-- 3. Index what the filters now use
CREATE INDEX IF NOT EXISTS clubs_usd_monthly_cents_idx
  ON clubs (usd_monthly_cents) WHERE status = 'approved';
DROP INDEX IF EXISTS clubs_monthly_cents_idx;
```

Then backfill rates by re-running the importer over your source spreadsheet, and
check for leftovers:

```sql
SELECT name, price_currency FROM clubs
 WHERE price_currency <> 'USD' AND fx_to_usd IS NULL AND price_period <> 'free';
```
